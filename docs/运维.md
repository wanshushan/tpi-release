# tpi-release 运维手册

> 这份文件由 `install.sh` 拷到服务器上（`/srv/tpi-update/README.md`、`/srv/tpi-site/README.md`），
> 所以断网时也能 `cat` 出来看。

---

## 1. 调度模型：为什么底层还有 systemd

```
1Panel → 计划任务                ← 调度权 100% 在这（周期 / 手动执行 / 日志 / 保留份数）
        │  执行 /usr/local/bin/tpi-*-sync.sh
        ▼
   task.sh （= tpi-release-sync.sh / tpi-site-sync.sh）
        │  systemctl start <unit>
        ▼
   tpi-*.service  (Type=oneshot)   ← 只提供只读沙箱，不做调度
        │  🔒 ProtectSystem=strict
        │     ReadWritePaths=<只列出真正需要的目录>
        ▼
   tpi-update-sync.py / tpi-site-deploy.sh    ← 真正干活的
        │  输出进 journald
        ▼
   task.sh 把本次日志捞回来 → 1Panel 执行记录
                            → 同时追加到 /var/log/tpi/*.log（自截断，2000 行）
```

**为什么要多这一层**：`ProtectSystem=strict` 让整个文件系统只读，只有 `ReadWritePaths` 列出的目录可写。
这两个脚本是全服务器唯一"从网络拉东西落到磁盘"的动作，沙箱保证它们**哪怕被喂了恶意上游，也碰不到
`/srv/tpi-update`（客户端正在读的元数据）以外的任何地方**。这是 HANDOFF 决策 #14 那条"结构性安全"。

**为什么不直接用 systemd timer**：调度权要集中在 1Panel（一个地方看全部任务）。
`.timer` 文件还在 `legacy/` 里，想退回 systemd 调度随时能退。

## 2. 任务 1：元数据同步

| 项 | 值 |
|---|---|
| 1Panel 任务名 | `tpi 元数据同步` |
| 脚本内容 | `/usr/local/bin/tpi-release-sync.sh` |
| 周期 | **每 1 分钟** |
| 建议保留份数 | 20 |
| 干活脚本 | `/usr/local/bin/tpi-update-sync.py` |
| systemd 单元 | `tpi-update-sync.service`（沙箱可写区 `/srv/tpi-update`） |
| 产物 | `/srv/tpi-update/update/latest.{yml,json}`、`history/<版本>/` |
| 日志 | 面板每次一行摘要；全量在 `/var/log/tpi/update-sync.log` |

### 面板上的三类摘要

| 你看到 | 含义 | 要处理吗 |
|---|---|---|
| `✓ 上游 v0.26.9 可达` | 拉到了，本地已是最新 | 不用 |
| `· 上游不可达，保持现有文件（正常降级）` | GitHub 超时，线上一个字节没动 | **不用**。约 5 次里 4 次是这个 |
| `✗ 出错（完整日志 …）` | 真的出错了 | 去看日志 |

### 上游为什么这么容易超时

服务器到 GitHub 实测约 **5 次里通 1 次**（每次卡满 30 秒 `urlopen error timed out`）。
`git clone` 实测要 **73 秒**。

**所以周期必须是 1 分钟**：1 分钟一次 → 平均约 5 分钟同步到。
拉长到 5 分钟 → 平均约 **25 分钟**才同步到。检查更新这条路对客户端是"永不失败"的要求，多试才划算。

### 三条不变量（排查时对照日志）

1. **失败不动现有文件** — 任何异常 → 退出码非 0 **且** `/srv/tpi-update/update/` 时间戳不变。
2. **关键资产 404 → 拒绝提升** — 日志会写 `关键资产不可下载 → 【拒绝提升】`。
   通常是你忘了传 `TutorPi-Setup-*.exe` / `TutorPi-*-win.zip`。
   漏 `.blockmap` 只告警不阻塞。**网络抖动（超时）不会阻塞** —— 免得把闸门卡死。
3. **`latest.yml` 是最后写入的**（先写 `latest.json`），两者都用 `.tmp` + `os.replace` 原子替换。

### 手动操作

```bash
sudo /usr/local/bin/tpi-release-sync.sh             # 等价于面板「执行」
sudo systemctl start tpi-update-sync.service        # 同上（跳过摘要，直接看 journal）
journalctl -u tpi-update-sync -n 50 -o cat --no-pager
tail -f /var/log/tpi/update-sync.log

sudo /usr/local/bin/tpi-update-sync.py --dry-run -v        # 只检查不写入
sudo /usr/local/bin/tpi-update-sync.py --force -v          # 内容相同也强制重装
sudo /usr/local/bin/tpi-update-sync.py --skip-asset-check -v   # 应急：跳过资产预检
ls -l /srv/tpi-update/update/history/                      # 历史版本
```

### 换上游 / 加备用源

改 `/etc/systemd/system/tpi-update-sync.service` 里的 `Environment=TPI_SYNC_SOURCES=`（逗号分隔、**按序回退**），
然后 `sudo systemctl daemon-reload`。第二个源放同名的 `latest.yml` / `latest.json` 就行 —
例如放 R2 上再填 `https://<R2域名>/meta`。

> 收益很大：R2 走 CF 边缘，从这台机可达性远好于 GitHub。加一个 R2 上游能让同步成功率从约 20% 变成接近 100%、
> 延迟回到 ≤60 秒。代价只是每次发版多拖两个几百字节的文件到 R2 控制台。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `TPI_SYNC_DEST` | `/srv/tpi-update/update` | 本地目标目录 |
| `TPI_SYNC_SOURCES` | GitHub `releases/latest/download` | 上游列表，逗号分隔按序回退 |
| `TPI_SYNC_HISTORY_KEEP` | `5` | 历史保留份数，`0` = 不留 |
| `TPI_SYNC_ASSET_TIMEOUT` | `20` | 资产预检单次超时秒数，`0` = 跳过预检 |
| `TPI_SYNC_REQUIRE_HOST` | `releases/download/` | yml 里每个 url 必须含该子串（防呆） |
| `TPI_SYNC_LOCK` | `<dest>/.sync.lock` | 防重叠锁文件 |

## 3. 任务 2：简介页部署

| 项 | 值 |
|---|---|
| 1Panel 任务名 | `tpi 简介页部署` |
| 脚本内容 | `/usr/local/bin/tpi-site-sync.sh` |
| 周期 | **每 5 分钟** |
| 建议保留份数 | 20 |
| 干活脚本 | `/usr/local/bin/tpi-site-deploy.sh` |
| systemd 单元 | `tpi-site-deploy.service`（沙箱可写区 `/srv/tpi-site` + 网站目录） |
| 网站目录 | `/opt/1panel/www/sites/tpi/index`（1Panel 静态站 `tpi`，端口 4477） |
| 回滚备份 | `/srv/tpi-site/www.prev` |
| 日志 | 面板回显全过程；全量在 `/var/log/tpi/site-deploy.log` |

### 三条硬性行为

1. **失败不动线上** — 任何一步出错都在 `rsync` 之前中止，网站目录一个字节不变。
2. **产物先校验再发布** — `index.html` 必须存在、必须是本站页面、字体必须在、体积 < 5MB。
3. **内容没变就不干活** — commit 与上次相同 → 直接退出，不构建、不写盘。

### 第 4 条：上游不可达 = 正常降级，不是失败

这台服务器到 GitHub 是**【间歇性】**可达的 —— 好的时候 `https://github.com` **0.45 秒返回 200**，
坏的时候 TCP 连接要卡 **135 秒**才失败（实测）。所以：

- 所有 `git` 操作都套 `timeout`（默认 120 秒，`TPI_SITE_GIT_TIMEOUT`）；
- 拉取失败 → `warn` + **`exit 0`**，线上一个字节不变，下一轮 5 分钟后重试。

> **为什么不是 `die`**：网络抖动不该在 1Panel 面板里显示成一片红叉。
> 这和 `tpi-update-sync` 的「上游无可用元数据 → 保持现有文件」是同一个哲学。

反过来说：**如果面板上连续很多轮都是「上游不可达」，那就是真的出问题了**，去看
`/var/log/tpi/site-deploy.log`，可能是网络被持续阻断，或者 `TPI_SITE_REPO` 写错了。

### 手动操作

```bash
sudo /usr/local/bin/tpi-site-sync.sh                       # 等价于面板「执行」
sudo systemctl start tpi-site-deploy.service
journalctl -u tpi-site-deploy -n 50 -o cat --no-pager
tail -f /var/log/tpi/site-deploy.log

sudo /usr/local/bin/tpi-site-deploy.sh --dry-run -v        # 只演练，不写盘
sudo /usr/local/bin/tpi-site-deploy.sh --force             # 忽略 commit 未变，强制重发
ls -la /srv/tpi-site/www.prev                              # 上一版
```

### 回滚到上一版

```bash
sudo rsync -a --delete --exclude 404.html --exclude .well-known \
  /srv/tpi-site/www.prev/ /opt/1panel/www/sites/tpi/index/
```

> `--exclude 404.html` 别省：那是 1Panel 生成的错误页，不属于我们的产物，删了它 1Panel 会当成"站点文件被改"。

### 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `TPI_SITE_MODE` | `pull` | `pull` = 只拉预构建产物；`build` = 在服务器上构建（见 `架构.md`） |
| `TPI_SITE_REPO` | `github.com/wanshushan/tpi-release.git` | 换镜像写这里。**必须是能被 `git clone` 的地方**（jsDelivr 不行，见下） |
| `TPI_SITE_BRANCH` | `main` | |
| `TPI_SITE_SRC_DIR` | `/srv/tpi-site/src` | git 工作副本 |
| `TPI_SITE_WEB_ROOT` | `/srv/tpi-site/www` | 部署目标 |
| `TPI_SITE_PREV_DIR` | `${WEB_ROOT}.prev` | 回滚备份目录 |
| `TPI_SITE_KEEP_PREV` | `1` | 是否保留上一版 |
| `TPI_SITE_SUBDIR` | `tpi-site` | 源码子目录 |
| `TPI_SITE_DIST_SUBDIR` | `tpi-site-dist` | 预构建产物子目录 |
| `TPI_SITE_GIT_TIMEOUT` | `120` | `git fetch` / `git clone` 单次超时秒数。超了就跳过本轮（不是失败） |

> ⚠️ **`TPI_SITE_PREV_DIR` 不能省**。`ReadWritePaths` 只放行网站目录**本身**，它的**父目录是只读的** ——
> 用默认的 `${WEB_ROOT}.prev`（即 `.../tpi/index.prev`）会以 `只读文件系统` 失败。
> 这就是 2026-10-11 那次 `tpi-site-deploy.service` 报 `failed` 的原因。

### 为什么不能用 jsDelivr 当拉取源

实测你这仓库在 jsDelivr 上的响应头：

```
Cache-Control: public, max-age=604800, s-maxage=43200
                                      ↑ CDN 边缘缓存 12 小时
```

另加两条硬伤：**不提供 `.git`**（没有 commit 就没法做"内容没变就跳过"，也没法回滚到某个版本）、
**不服务 GitHub Release 资产**（元数据那条路它够不着）。

jsDelivr 唯一在用的地方是 `install.sh` 的**兜底抓取**（只 curl 了一个脚本、配套文件不在旁边时），
正常 `git clone` 仓库后跑 `install.sh` 根本不走它。

## 4. 一键清理旧部署残留

```bash
sudo bash tools/tpied_clear.sh --dry-run     # 先看要做什么，一个字节不动
sudo bash tools/tpied_clear.sh               # 停旧 timer + 删公网可见的残留
sudo bash tools/tpied_clear.sh --purge       # 连 .timer 单元文件一起删
sudo bash tools/tpied_clear.sh --keep-timers # 先别停 timer（1Panel 任务还没建好时用）
```

**它绝对不碰**（写死在 `guard_path()` 里，不是靠"忘了写"）：

- `/srv/tpi-update/update/**` — 客户端正在读的 `latest.yml` / `latest.json`
- `/srv/tpi-update/update/history/**` — 回滚用的历史版本
- `/usr/local/bin/tpi-*` — 干活的脚本本体
- `/etc/systemd/system/tpi-*.service` — 沙箱执行器（1Panel 任务靠它干活）
- `/srv/tpi-site/src` — 部署脚本的 git 工作副本

**它会处理**：旧 `.timer`（停用，`--purge` 才删）、网站目录里的 `dist.zip` / `index.prev`、
旧的服务器文档副本（`README-SYNC.md` / `README-SITE.md`）、空的 `/srv/tpi-site/www`。

## 5. 回滚：退回 systemd timer 调度

```bash
sudo systemctl enable --now tpi-update-sync.timer tpi-site-deploy.timer
```

`.timer` 文件在仓库的 `legacy/` 里；`install.sh --with-timer` 也会把它装上。
**注意别和 1Panel 任务同时开**（虽然脚本内 `flock` 保证不会并发，但日志会翻倍）。

## 6. 排障速查

| 症状 | 先看 |
|---|---|
| 客户端检查更新拿到旧版本 | `curl -s http://127.0.0.1:5757/update/latest.json \| head -c 80`，再看任务 1 的面板摘要 |
| 下载安装包失败 | `curl -sI http://127.0.0.1:5757/releases/download/v<版本>/<文件>` 要 **302**；R2 的 key 是 `releases/`（复数） |
| 页面还是旧的 | 任务 2 面板；`ls -la /opt/1panel/www/sites/tpi/index/`；确认 `tpi-site-dist/` 真的提交了 |
| 首页背景不见了（只剩纸白底） | 是**预期内的静默降级**：背景是 WebGPU 组件，任何 GPU 错误都只回调 `onError`。① 浏览器不支持 WebGPU（Chrome/Edge 113+ 才有）；② `vgpu` 被升到了 0.5.x —— 组件只兼容 0.4.x，见 `tpi-site/README.md` 的「背景」；③ 打开控制台看有没有 `ValidationError` |
| 改了文案但字形不对（像是换了字体） | 漏跑 `npm run fonts`。字体是按页面上用到的字符切子集的，见 `tpi-site/README.md` 的「字体」 |
| 文案改了构建失败 | 大概率是 `tpi-site/src/content/index/index.mdx`：`title` / `description` 少了，或 `<Slogan>` 的 `lines` 是空的（错误信息会直接点名） |
| 页面 404 / 空白 | `curl -sI http://127.0.0.1:4477/`；再 `curl -sI https://tpi.wanshushan.top/`；Caddyfile 里 `:5757` + `bind 127.0.0.1` 不能写主机名 |
| 部署服务 `failed` | `journalctl -u tpi-site-deploy -n 40 -o cat`。`只读文件系统` → `TPI_SITE_PREV_DIR` 没设对 |
| 部署任务显示「上游不可达，跳过本轮」 | **正常降级**。这台机到 GitHub 是间歇性的，下一轮会自动重试。连续很多轮都这样才是真问题 |
| 改了 Caddyfile 没生效 | `caddy validate --config /etc/caddy/Caddyfile && systemctl reload caddy` |
| CF 缓存住了旧响应 | `curl -sI "https://tpi.wanshushan.top/?cb=$RANDOM"` 对比；是缓存就去 CF purge（**别 purge `/releases/`**，那有 20 小时 302 缓存） |
| 刚重新切了字体，部分访客还是旧字形 | `/fonts/*` 带 `max-age=72000`（20 小时），而且 URL 不带指纹 —— 每次重切字体后建议顺手 purge `https://tpi.wanshushan.top/fonts/*`。JS 不用管：`_astro/*` 自带内容哈希 |

## 7. 迁移记录（2026-10-11：systemd timer → 1Panel 计划任务）

**动因**：原来运维面分散（systemd timer + Caddy + 1Panel + CF Dashboard），
看日志要翻 README，手动跑要记 `systemctl` 命令。

**处置**：

| 之前 | 之后 |
|---|---|
| `tpi-update-sync.timer`（每 1 分钟） | 1Panel 计划任务 `tpi 元数据同步`（每 1 分钟） |
| `tpi-site-deploy.timer`（每 5 分钟） | 1Panel 计划任务 `tpi 简介页部署`（每 5 分钟） |
| 配置在 `.service` 的 `Environment=` 里 | 配置仍在 `.service`（由 `install.sh` 写入），**但日常不用改** —— 周期在面板改 |
| 日志靠 `journalctl` | 面板执行记录（摘要）+ `/var/log/tpi/*.log`（全量） |
| `server/` 12 个文件平铺 | `update-sync/` + `site-deploy/` 两套自洽目录 |
| 三处讲运维的 README | 本文件 + `架构.md` + 根 `README.md` 的速查表 |

**保留 systemd 单元的理由**：它现在只当"只读沙箱"，不当"调度器"。成本是多一层调用，收益是
`ReadWritePaths` 那层结构性安全。这是个**可逆**决定 —— 任务内容改成直接跑
`/usr/local/bin/tpi-*-deploy.sh` 就放弃了加固，改回去也只要一行。

**已知的坑（都踩过）**：

1. `ReadWritePaths` 只放行网站目录本身 → 网站目录的**父目录只读** → 回滚备份不能放 `index.prev`。
2. `rsync --delete` 会删掉 1Panel 的 `404.html` → 必须 `--exclude 404.html`。
3. 网站目录里手工留了 `dist.zip` → 它会被公网直接下载（`https://tpi.wanshushan.top/dist.zip` 返回 200）。
4. `update-sync/test.py` 里 `SYNC` 指向 `scripts/server/`（这些文件还住在 Tutor_pi 仓库时的路径），
   搬过来之后测试一直是坏的 → 改成按本文件位置定位；`subprocess.run` 补 `encoding="utf-8"`
   （Windows 上 `text=True` 默认用 GBK 解码 → `stdout=None`）。
5. **服务器到 GitHub 是间歇性的**（2026-10-11 实测）：
   - `https://github.com` 好的时候 **0.45 秒 → 200**；坏的时候 TCP 连接 **135 秒**才失败。
   - DNS 是干净的（`github.com` → `20.205.243.166`，真实 IP），**不是污染，是间歇性阻断**。
   - 所以 `git fetch` 加了 `timeout`，并且把拉取失败从 `die` 改成了正常降级。
   - `cdn.jsdelivr.net` 这台机上**只解析出 IPv6**（A 记录被吞）—— 别指望它当备用源。
   - 万不得已的离线通道：`git bundle`。本地 `git bundle create x.bundle main`，
     服务器 `git -C <clone> fetch --no-tags x.bundle main && git reset --hard FETCH_HEAD`。
     128KB，完全不碰 GitHub。
