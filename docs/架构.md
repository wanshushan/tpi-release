# 架构：为什么这样设计

> 「怎么做」在 `运维.md`。这份只讲「为什么」—— 改这套东西之前先读完。

---

## 1. 客户端只认一个域名

`electron/updater.cjs:47-51` 里写死了：

```js
const PUBLIC_BASE = "https://tpi.wanshushan.top";
const DEFAULT_FEED_BASE = `${PUBLIC_BASE}/update/`;
const ALLOWED_FEED_PREFIXES = [`${PUBLIC_BASE}/`];
```

所以客户端只会请求两样东西，**都在同一个源上**：

| 请求 | 用途 |
|---|---|
| `https://tpi.wanshushan.top/update/latest.{yml,json}` | 检查更新（几百字节） |
| `https://tpi.wanshushan.top/releases/download/vX/<文件>` | 下载字节（185MB，**302 到 R2**） |

**这个白名单是整套设计的地基**：只要 `tpi` 这个域名上的路径不变，后面换字节宿主、换服务器、
换调度方式，客户端**零改动**。

---

## 2. 三条不可动摇的约束

### ① 不自建带宽

185MB 的安装包**不走自家服务器**。服务器只做「几百字节的版本检查 + 302 调度」。
字节放在 **Cloudflare R2**（桶 `tpi-release`，域名 `tpirelease.wanshushan.top`）。

> 为什么不能复用 `tpi.wanshushan.top`：一个主机名只能有一条 CF 路由。概念上也该分开 ——
> `tpi` = 元数据端点，`tpirelease` = 字节仓库。

### ② 纯静态 + 手动闸门

**无 CI、无 PAT、零 token**。只有用户显式在 GitHub 上操作（把 release 设为 latest）才开门。
服务器只有**出站拉取**，没有任何入站写入口。

### ③ 日常发布不碰 SSH

SSH 只是破窗路径。发版全在 GitHub 网页上点。

---

## 3. 为什么元数据必须本地化

> **「450B 的依赖 ≠ 185MB 的依赖」**

客户端**检查更新**这条路必须**永不失败** —— 失败了用户就永远发现不了新版本，而且没有任何补偿手段。
**下载字节**失败了可以重试、换镜像、手动去 GitHub 下。

所以：元数据从 GitHub 同步到服务器本地，客户端读**本地文件**。上游挂了（404 / 超时 / 内容不合法）时，
同步脚本什么都不改，线上继续用旧元数据 —— 已经发布出去的更新检查完全不受影响。

**实测依据**：这台服务器直连 GitHub 约 **5 次里通 1 次**（每次卡满 30 秒超时）。
如果不做本地化，客户端每次检查更新都有 80% 概率失败。

### 为什么字节走 R2 而不是 GitHub

本机实测同一批 URL 连试三次：`206 / 206 / 超时`；而**直连 GitHub 三次全超时**。
`github.com` 的 **DNS 解析要 5.17s 而 TCP 只要 0.16s**（纯 DNS 问题）。
换到 R2 后 `cf-cache-status: HIT`，从中国访问明显快。

**副作用（正面）**：每次发布的 GitHub 上传量从 **410MB 降到 1.9KB** ——
GitHub 只留元数据当闸门通道 + 公开记录。

## 4. 闸门在哪：GitHub，不在服务器

| 你做什么 | 结果 |
|---|---|
| 建 release 时勾 `prerelease` | `releases/latest` 会**跳过**它 → 客户端看不到 |
| 点 **Set as the latest release** | ≤60 秒后服务器同步到 → **闸门打开** |
| 在旧 release 上再点一次 **Set as the latest release** | ≤60 秒后回滚 |

因为服务器是「拉最新」，而「最新」由 GitHub 的 latest 语义定义 —— 所以闸门天然在 GitHub 上，
纯网页、零 token、可撤销。

---

## 5. 安全性质：服务器只读

**服务器被攻破也无法伪造 `latest.yml`。** 这是**结构性**安全，不是配置性的：

- Caddy **只服务本地文件**，没有任何写权限；
- 唯一会写 `/srv/tpi-update/update/` 的是 `tpi-update-sync.py`，而它跑在 systemd 的
  `ProtectSystem=strict` + `ReadWritePaths=/srv/tpi-update` 沙箱里 —— **整个文件系统对它只读，除了那一个目录**；
- 所以一个"从网络拉字节"的脚本，物理上碰不到它不该碰的地方。

R2 那边也一致：只存字节，**不放** `latest.yml` / `latest.json`（那俩由 Caddy 从本地发）。

### 沙箱怎么和 1Panel 调度共存

调度器换成了 1Panel 计划任务，但**沙箱还是 systemd 的**：

```
1Panel 计划任务 → tpi-release-sync.sh → systemctl start tpi-update-sync.service → 沙箱里干活
```

于是「一个地方看全部任务」和「结构性安全」同时成立。成本只是多一层调用。

简介页那边是同一套结构：`/usr/local/bin/tpi-site-sync.sh` → `systemctl start tpi-site-deploy.service`。
所以 **1Panel 任务的脚本内容必须是那个 `*-sync.sh` 入口**：直接写 `tpi-site-deploy.sh`
就等于跳过单元 —— 没有沙箱，也拿不到单元里的 `Environment=TPI_SITE_*`，配置会退回
默认值 `/srv/tpi-site/www`，而 1Panel 静态站服务的是 `/opt/1panel/www/sites/tpi/index`。
2026-10-14 那个「面板全绿、页面不变」就是这么来的。

**这是可逆的**：把 1Panel 任务内容改成直接跑 `/usr/local/bin/tpi-update-sync.py`
就放弃了这层加固（`task.sh` 里那段 `systemctl start` 就是全部代价）。

## 6. `pull` 还是 `build`：简介页的两种模式

| | `pull`（默认） | `build` |
|---|---|---|
| 服务器做什么 | `git fetch` + 复制 `tpi-site-dist/` 到网站目录 | `git clone` + 在 Docker 里 `npm ci && npm run build` |
| 服务器上有 Node 吗 | 没有 | 有（容器里） |
| 执行仓库代码吗 | **不执行** | **执行** |
| 与「服务器只读」相容吗 | ✅ | ❌ 引入「仓库代码 → 服务器执行」这条路径 |

**代价**：`pull` 模式要求每次改页面后**本地**跑 `npm run publish` 并把 `tpi-site-dist/` 一起提交。
忘了提交 → 线上还是旧页面（因为服务器只读那一个目录，它和源码不一致时线上就是旧的）。

**为什么默认 `pull`**：服务端构建会实质回退「服务器只读」这条性质 —— 一个能执行
`package.json` 里 `postinstall` 脚本的服务器，不再是一个"被攻破也没用"的服务器。

要切 `build`：改 `.service` 里的 `TPI_SITE_MODE=build`，并把加固段换成 `build` 模式那一组
（那组需要放行 docker socket，加固必然弱很多）。

## 7. 版本路线（为什么有「载具版本」）

```
0.26.4          无更新器 —— 无法自我验证
0.26.5  载具    手动装一次，把更新器装进机器；永久 prerelease，永不提升
0.26.6          首个对外发布版本
0.26.7  载具    手动装一次；prerelease 不提升
0.26.8          已正式发布并提升为 latest；0.26.7 → 0.26.8 非静默更新已真机验收
0.26.9          当前
```

**「载具版本」的作用**：更新器只能被"已经装着更新器的客户端"拉到。所以每个大改动都需要一个
手动安装的载具版本，把新版更新器送进机器，之后靠它把真正的发布版拉下去。
载具版本**永远保持 prerelease**，这样它不会出现在 `releases/latest` 里被普通用户看到。
